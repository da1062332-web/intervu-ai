Infrastructure & capacity audit

Concurrency Readiness Audit

Can the platform serve 2,000 candidates sitting an assessment at the same moment, without errors? A file-level review of the execution, database, and monitoring layers behind app.skillitrix.com.

Target load 2,000 concurrent candidates Branch beta Deploy target Render — single "starter" service
Not ready

At 2,000 concurrent candidates, the platform will fail before it scales gracefully. Three independent hard blockers — a code-execution tunnel with no redundancy, a multiplying database connection pool, and submission transactions that queue on a handful of pooled connections — each cap real capacity far below the target on their own. No commit or test found evidence this has been run at anywhere near 2,000 concurrent users through the real request path.

Critical blockers

Any one of these would cause candidate-facing errors well under 2,000 concurrent users; together they compound.

Critical · code execution

Every coding submission crosses one local machine and a free ngrok tunnel

JUDGE0_URL points at marbled-fifty-unraveled.ngrok-free.dev — a static ngrok domain tunnelled to a Docker Judge0 instance on someone's local Windows PC, started manually via a batch script. render.yaml deploys no Judge0 service at all; production has no execution infrastructure of its own.

Submissions aren't queued either: POST /coding/run and /coding/submit call Judge0 synchronously inside the HTTP request, looping test cases one at a time with no rate limit on the endpoint. This is the hardest ceiling in the system — any assessment with coding questions saturates one machine and one tunnel, with no fallback.

apps/api/.env — JUDGE0_URL start-judge0-tunnel.bat coding-execution.controller.ts judge.service.ts
Critical · database

The Prisma connection pool is being multiplied, not shared

The API and the background worker share one Node process, but each builds its own PrismaClient — and worker code goes further, calling new PrismaClient() per invocation rather than reusing one. Every one of these opens its own pool against the same Supabase pgbouncer budget (a handful of connections on a starter tier). Under real concurrent load this exhausts the pool and surfaces as P1017/P2024 timeout errors directly to candidates.

apps/api/src/prisma/prisma.service.ts packages/database/src/client.ts apps/worker/src/services/ai.service.ts:64 apps/worker/src/queues/generation.queue.ts:22
Critical · submission path

Submit transactions hold scarce connections through the deadline spike

The submit flow wraps status updates, submission-count checks, and event writes in one prisma.$transaction with a 90-second timeout and 60-second max wait. Under pgbouncer's transaction-mode pooling, that transaction occupies one of only a handful of pooled connections for its full duration. When candidates submit together near a shared deadline — the realistic worst case — submissions queue against that tiny pool instead of running in parallel, producing multi-second to multi-minute submit delays at the exact moment candidates can least tolerate them.

Secondary risks

These raise error rates and latency under load without being an immediate hard wall on their own.

High · deployment

One unclustered process on a "starter" instance runs everything

The API, the BullMQ worker, and all queue processors run inside a single Node process (scripts/start-combined.js), on one Render "starter" plan instance — roughly 0.5–1 vCPU, no horizontal scaling, no cluster/PM2. WORKER_CONCURRENCY=2 is set in render.yaml but ignored: queue processors hardcode their own concurrency (e.g. evaluation at 3) directly in code. There is no path to add capacity short of changing the deploy topology.

render.yaml scripts/start-combined.js:87,125 evaluation.queue.ts:39
High · autosave

Autosave costs 3–4 uncached DB round trips per save

Every answer autosave hits examConfig.findUnique and, in some flows, testInstanceQuestion.findFirst — neither cached — plus two upserts, all synchronous in the request. At 2,000 candidates autosaving every 10–15 seconds, that's roughly 400–800 database statements per second sustained from this path alone, competing with the same undersized connection pool described above.

autosave.service.ts:23-230 answer.controller.ts:43-55
High · admin monitoring

The live monitoring dashboard re-pulls the full candidate cohort on every poll

getAssessmentLiveSnapshot runs an unpaginated testInstance.findMany with deep joins (user, execution state, submissions, questions) across every active candidate, then sorts and filters in JavaScript — on every dashboard load, filter change, and background poll. It sits behind a Redis fast-path, but that cache overlays live fields onto rows still pulled fresh from Postgres each time, so it doesn't actually reduce the query's cost. This scales linearly with candidate count on every admin refresh, sharing the same process as candidate-facing traffic.

What already holds up

Not everything needs to change — these parts were built with scale in mind.

Holds up

Candidates never open a persistent connection

Real-time monitoring is SSE for admins only; candidates send a 15-second heartbeat over plain REST. Connection count scales with open admin tabs, not with the 2,000 candidates, so this layer isn't a bottleneck at target load.

Holds up

Indexing on the assessment-taking path is solid

TestInstance, CandidateAnswer, ExecutionState, and related models carry indexes matching their actual query patterns, including the composite key the autosave upsert relies on. No full-table-scan risk found on the hot path.

Holds up

Submission idempotency uses a per-candidate lock, not a global one

The Redis distributed lock on submit is keyed per testInstanceId, so one candidate's submission never blocks another's. It's the transaction's connection-hold time that's the problem, not this locking design.

Remediation roadmap

Ordered by what has to be true before the next phase is worth doing.

01Unblock

Remove the two hard walls

Move Judge0 off the local-machine ngrok tunnel onto real hosted or self-hosted infrastructure with its own scaling. Fix the PrismaClient multiplication — one shared client per process, explicit connection_limit on DATABASE_URL, and a Supabase pooler size to match.

Nothing else is worth testing until both land
02Decouple

Take execution and scoring off the request thread Implemented

Route coding submissions through a BullMQ queue instead of running synchronously inside the HTTP handler. Shrink or remove the interactive submit transaction, or move that path off transaction-mode pooling entirely. Add rate limiting to the coding endpoints.

New code-execution BullMQ queue with a bounded-concurrency processor (CODE_EXECUTION_CONCURRENCY, default 6) sits between the controller and Judge0, with a queue-depth check that returns 503 once too many jobs are in flight instead of piling up. coding-execution.controller.ts now enqueues and awaits the job instead of calling Judge0 inline. The submission transaction was cut from a 90s/60s budget down to 15s/10s by moving the read-only answer fetch out of it entirely. run is now rate-limited under the assessment bucket, submit under the dedicated submission bucket (5/min) that already existed in config but was unused.
03Scale out

Split the deploy topology Implemented

Run the worker as its own Render service instead of co-located with the API, and enable horizontal scaling (multiple API instances) rather than relying on one starter-plan process.

render.yaml now defines intervu-api and intervu-worker as separate Render services with their own start scripts (scripts/start-api.js, scripts/start-worker.js); the worker calls back to the API over INTERNAL_API_URL and waits for its health check before processing jobs. Still open: actual horizontal autoscaling (minInstances/maxInstances) needs a Render plan tier above "starter" — the block is documented inline in render.yaml ready to uncomment once upgraded.
04Tighten

Reduce write volume on hot paths Implemented

Batch or debounce autosave writes, and rework the admin monitoring snapshot to filter and paginate in SQL rather than pulling the full cohort into JavaScript on every poll.

Autosave now caches the section-navigation flag (10 min TTL) and per-question section-lock status (5s TTL) in Redis, cutting two uncached DB round trips down to roughly one every 5 seconds of rapid saving instead of one per save. The admin snapshot query trims executionState to the five fields actually used, replaces a full questions row pull with a _count, and caps the query at 5,000 rows so an unfiltered "all assessments" view can no longer scale unbounded with total candidate history.
05Prove it Implemented

Load-test the real path

Run k6 or Artillery against the actual public API — auth included, coding submissions included — ramping to 2,000 concurrent virtual users, before trusting this at scale in production.

load-tests/k6-2000-candidates.js drives signup/login → start test → autosave loop → optional coding run/submit → final submit through the real public API, ramping to a configurable MAX_VUS (default 2,000), with pass/fail thresholds on error rate and p95 latency. See load-tests/README.md — it still needs to actually be run against staging with a real testConfigId to get a verified number.
Run it — this is the only step that turns "should work" into "does work"
